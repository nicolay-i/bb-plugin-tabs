# Правила локальной разработки

Проект проверяется локально. CI/CD для этих проверок не используется.

## Обязательные проверки

- Перед завершением изменений запускай `npm run check`. Команда проверяет форматирование, ESLint, TypeScript и весь набор тестов.
- После изменения кода плагина или CSS дополнительно запускай `npm run build`. Для сборки нужен установленный BB CLI.
- Не сообщай, что работа завершена, пока проверки не прошли. Если проверка заблокирована окружением, явно укажи команду, причину и непроверенную часть.
- Не отключай правила, не добавляй `any`, `@ts-ignore`, пропуски тестов или исключения из проверок только ради зелёного результата. Исправляй причину; обоснованное исключение должно быть узким и описанным.
- Форматирование исправляй через `npm run format`, затем повторяй `npm run check`. Автоматическое форматирование не заменяет просмотр diff.
- В итоговом сообщении кратко указывай выполненные проверки и их результат.

## Работа с кодом

- Сохраняй существующее поведение и пользовательские незакоммиченные изменения. Не делай попутный массовый рефакторинг.
- На новое нетривиальное поведение добавляй воспроизводимую проверку. Для багфикса сначала проверь все пути вызова изменяемой функции.
- Тестовые RPC-моки должны соответствовать `rpcContract`. В `test-utils.ts` находятся адаптеры старого SDK harness: отсутствующие mock handlers по-прежнему отклоняют вызов, а заданные handlers проверяются по типам.
- `components/ui/` — vendored-компоненты BB: они исключены из ESLint и Prettier, но остаются под проверкой TypeScript и публичного SDK. Не переформатируй их без отдельной необходимости.
- Для UI-изменений проверь затронутый сценарий в работающем BB на нужных desktop/mobile поверхностях. После успешных проверок и сборки перезагрузи только плагин `tabs`: `bb plugin reload tabs`. Если визуальная проверка не выполнена, честно укажи это.
- Не меняй версии BB SDK и зависимости без необходимости. При добавлении зависимостей проверяй совместимость и вывод `npm audit`; не запускай слепой `npm audit fix --force`.

## Производительность BB-плагинов

- Перед изменениями кода или CSS прочитай `docs/bb-plugin-performance.md`. Проверяй не только работу компонента, но и общестраничное инвалидирование CSS, повторные RPC, observers и layout; не добавляй глобальные `body:has(...)`/`html:has(...)` без обоснования замерами.
- Для performance-изменений сохраняй воспроизводимые baseline → candidate → baseline и ограничения измерения в `.tmp/`; синтетика и traced latency не заменяют проверку целевого сценария в работающем BB.
- Перед публикацией обязательно проверь регрессии производительности; найденные ухудшения исправь, отладь и повторно проверь. Оптимизация не должна ослаблять корректность, доступность или сохранность пользовательских данных.

## Команды

- `npm run check` — обязательная полная локальная проверка.
- `npm run lint` — ESLint: JS/TS, promises и правила React Hooks.
- `npm run format:check` / `npm run format` — проверка / применение Prettier.
- `npm run typecheck` — проверка типов исходников и тестов.
- `npm test` — весь Vitest-набор; `npm test -- <файл>` — отдельные тесты.
- `npm run build` — сборка плагина через BB CLI.

Always run `tree docs` at the beginning to get an overview of durable documents. Before changing documentation read `document_writing.md`.
