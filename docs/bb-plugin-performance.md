# Быстрые плагины BB: работа, стили и проверка результата

Гайд для разработки BB-плагинов по результатам расследования переключения чатов в Chat Tabs. Это требования к новым изменениям, а не утверждение, что все описанные проблемы уже исправлены в опубликованной версии.

## Сначала исключи ненужную работу

- Не загружай данные закрытого меню или скрытой поверхности без другого потребителя. Не превращай каждый render, смену чата или realtime-сигнал в полный reload всех данных.
- Используй существующие helpers, индексы, подписки и очереди. Строй общий индекс один раз на актуальный snapshot, а не повторяй обходы для каждой вкладки и каждого компонента. Не добавляй абстракции или зависимости без измеренной необходимости.
- Предпочитай события polling-у. Объединяй всплеск событий, ограничивай размер snapshot, pagination и параллельные запросы; no-op не должен порождать запись и новую волну realtime.

## Глобальный CSS может тормозить чужой UI

`body:has(...)` — не бесплатный способ узнать, открыт ли чат, modal или панель. В расследовании Chat Tabs изменения main chat планировали инвалидирование `:has()` на `BODY`, а общий invalidation set затем помечал сотни native hover-элементов сайдбара. Они заново проходили сопоставление со стилями BB и других плагинов, хотя пользователь нажимал вкладку.

- Не используй `body:has(...)`, `html:has(...)` и другие общестраничные зависимости как обычный мост между плагином и native layout. Предпочитай состояние и селекторы в границах своей поверхности; исключение требует замера инвалидирования на реальной странице BB.
- Scoped utilities тоже стоят времени: общие классы вроде `flex` и `items-center` могут быть кандидатами для правил многих stylesheet, даже когда проверка plugin root в итоге их отвергает. Сокращай ненужные utilities в своём bundle, но не удаляй сгенерированные SDK-правила лишь потому, что такие декларации есть в текущем CSS хоста.
- Совпадение деклараций ещё не означает эквивалентность каскада. Удаление позднего повтора может открыть другое правило, а `@scope` добавляет scoping proximity. На сохранённых стилях BB перенос в `@scope` изменил результат `flex grid` внутри вложенных плагинов. Проверяй вложенные roots, root без id, порталы, conflicting classes и состояния, а не только один screenshot.

Локальный `:has()` не запрещён сам по себе. Проверяется область и частота инвалидирования; верхняя строка selector statistics не доказывает, что её замена ускорит весь сценарий.

## DOM-наблюдение и layout без циклов

- Собирай измерения в существующий `requestAnimationFrame`: сначала все чтения, затем записи. Чтение `scrollWidth` или `getBoundingClientRect()` может оплатить уже накопленный style/layout всей страницы; перенос этого чтения в другую функцию не устраняет первопричину.
- Пиши размеры, атрибуты и React state только при изменении значения. `ResizeObserver` не должен безусловно менять наблюдаемую геометрию. Наблюдателям нужны cleanup, отмена кадра и отсутствие собственных mutation-циклов.
- Если CSS-condition заменяется DOM-флагом, сохрани исходную логику, специфичность и семантику «есть хотя бы один подходящий элемент». `getElementById()` первого overlay не эквивалентен `:has(#overlay[condition])` при нескольких overlay. Учитывай переходные mounts, main/sidechat, inert/modal, split и fullscreen/drawer; переиспользуй существующее наблюдение и узкий `attributeFilter`, а не вводи polling или глобальный observer на каждую вкладку.
- Не ускоряй навигацию ценой фокуса, вертикального scroll или ручной горизонтальной прокрутки. Например, раскрытие активной вкладки нужно при смене active identity или доступной ширины, а не при каждом обновлении статуса.

Сценарии геометрии и фокуса описаны в [responsive-layout.md](responsive-layout.md) и [hover-and-focus.md](hover-and-focus.md).

## RPC: устрани повторный запрос, но сохрани корректность

- Дорогой inventory окружения не должен перечитываться для каждого чата, если область данных не изменилась. Объединяй одновременно выполняющиеся read-only запросы по реальному ключу данных, например project/environment. TTL допустим только при обоснованном сроке свежести; transient failure нельзя навсегда кешировать как недоступность.
- Поздний ответ проверяй по актуальному запросу, поколению или ревизии. A→B→A и ответ после unmount не должны откатывать новое состояние. Оптимизация не отменяет сериализацию mutations, проверку входа, lifecycle authority и validate/write-before-publish.
- Не путай ожидание соединения до отправки HTTP с временем backend-обработчика. Сохраняй pending, failed и completed запросы; учитывай транспорт целевого клиента. Очередь соединений локального HTTP-прогона не доказывает такую же очередь в удалённом HTTPS-клиенте.

Согласованность и ограничения кешей — в [synchronization-and-errors.md](synchronization-and-errors.md).

## Как измерять

1. Назови пользовательский сценарий: переключение чата и переключение режима — разные операции. Замеряй не только обработчик клика или active-highlight, но и появление содержимого именно целевого чата. Два `requestAnimationFrame` дают возможность отрисовки, а не подтверждение фактического показа пикселей.
2. Измеряй на целевой поверхности. Локальный headless не заменяет удалённый браузер пользователя, BB Desktop или физическое мобильное устройство. Фиксируй viewport, панели, набор чатов/размер DOM, версии BB/SDK, прогрев и нагрузку хоста во время прогона.
3. Чередуй baseline → candidate → baseline с одинаковыми условиями. Разделяй холодный старт и тёплые переходы, указывай число измерений, обычную медиану и разброс. Один быстрый переход или загруженный хост не дают надёжного процента ускорения.
4. Разделяй wall-clock, renderer CPU, style, layout, JavaScript и сеть. Для поддерживаемого Chromium полезны CDP Performance metrics с `timeDomain: "threadTicks"`; при недоступности явно укажи другой clock. Метрики за окно наблюдения не равны исключительно работе до первого кадра; вложенные/inclusive интервалы нельзя просто складывать.
5. Трассируй отдельно от обычного benchmark. Selector statistics и invalidation tracking сами заметно замедляют страницу. Используй их для поиска цепочки причин и количества лишних restyles, но не выдавай traced latency за обычную. Место дорогого geometry-read — ещё не доказательство виновности вызывающей функции.
6. Для общей CSS-гипотезы добавь небольшой CSS-only контроль без React/RPC, но затем проверь вывод в настоящем BB. Укажи, есть ли над элементами именованный, безымянный или вложенный plugin root: rootless-синтетика может показывать выигрыш, которого нет в приложении.
7. Сравни фактически применённые свойства и геометрию, затем проверь затронутые UI-состояния. Пустая разница выбранных computed properties не доказывает совместимость всех hover/focus, media queries, порталов, анимаций и host-версий. Новую стратегию селекторов проверяй и с чистого запуска; предполагаемые внутренние кеши браузера не объявляй установленной причиной без отдельного опыта.

## Что должно остаться после оптимизации

- Минимальный воспроизводимый regression check на причину, а не только на новый текст реализации. Сохраняются клавиатура, focus, reduced motion, RTL, очистка ресурсов, stale-response защиты и поведение desktop/mobile.
- Артефакты до/после, конфигурация, число замеров и ограничения — в `.tmp/` проекта. RPC-подмены только локальные и соответствующие контракту; mock-rendering и настоящая сеть измеряются отдельно. Не меняй пользовательские чаты и настройки ради benchmark и не откатывай старый snapshot поверх параллельных изменений.
- В этом проекте SDK-аудит проверяет и JavaScript внутри `.tmp/`: диагностические `.js`/`.cjs`/`.mjs` и сгенерированные кеши диагностических инструментов после прогона архивируются, а не обходятся исключением из allowlist.
- Собственный браузер закрывается в `finally`/watchdog. Очистка идентифицирует точный executable и принадлежащий тесту profile, а не случайное совпадение строки команды.
- Пройдены `npm run check`, а после изменения кода/CSS — `npm run build`; проверен diff. Для UI выполнены нужные живые desktop/mobile сценарии, затем перезагружен только затронутый плагин. Невыполненное явно отмечено.
- Перед публикацией повторён performance-regression контроль. Найденные ухудшения исправлены, отлажены и повторно проверены. Нет обещания ускорения только по уменьшению кода, одной трассе, синтетическому коэффициенту или визуально более раннему highlight.
