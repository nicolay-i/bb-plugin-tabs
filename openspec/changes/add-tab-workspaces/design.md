## Context

Мотивация и границы пользовательского поведения — в `proposal.md` и `specs/tab-workspaces/spec.md`.

Сейчас `TabsState` содержит один набор `entries` и независимый `favorites`. В `server.ts` состояние, история и `tabs.closedThreads.v1` используют общую очередь `mutationTail`; lifecycle reconciliation обрабатывает только один набор. В `app.tsx` несколько экземпляров `useTabsState` обслуживают полосу и New chat, принимая все события `tabs-changed` без идентификатора набора. Очереди и дедупликация запросов также не различают workspace.

## Goals / Non-Goals

**Goals:**

- Сохранить существующую модель одного набора и её тестируемые функции.
- Разделить постоянное содержимое режимов и временный выбор окна.
- Держать выбор единым для всех поверхностей одного окна, не делая его серверным глобальным состоянием.
- Мигрировать старые данные без перезаписи и защититься от межрежимных гонок.

**Non-Goals:**

- Изолировать доступ к чатам, фильтровать sidebar или общую историю по workspace.
- Переключать BB environments, Git worktrees, проекты или рабочие каталоги.
- Автоматически открывать последний чат режима, копировать наборы, вводить вложенные workspace или индивидуальные настройки темы.
- Выпускать и публиковать релиз в рамках реализации этой задачи.

## Decisions

### 1. Коллекция наборов поверх существующего TabsState

Добавить небольшую модель workspace со стабильным ID, именем, `TabsState` и `closedThreadIds`. Прежние helpers продолжают изменять только переданный набор; переименование не меняет ID. Пользовательские имена — обычный текст, не HTML и не ключи перевода. Начальные имена локализованы; после пользовательского переименования текст не переводится.

Коллекцию хранить одним версионированным JSON envelope с монотонной `revision` в одной строке встроенной SQLite, предоставляемой `bb.storage.database()`. Таблица создаётся через append-only `bb.storage.migrate`. Это позволяет атомарно сохранить миграцию и изменения нескольких наборов в существующей серверной очереди без многоключевых транзакций. Историю оставить в `tabs.history.v1`; legacy KV-ключи не менять.

Уточнение после проверки SDK: KV имеет предел 256 КБ на значение, поэтому не подходит для 20 заполненных наборов по 100 вкладок и 100 избранных. Отдельный KV-ключ для каждого режима усложняет атомарную миграцию и lifecycle reconciliation. Одна строка SQLite сохраняет простую модель envelope, не добавляет зависимостей и избегает этого ограничения. При измеренной проблеме полного чтения/записи можно перейти к строке на workspace. Ограничения имён: обрезка крайних пробелов, 1–80 символов, запрет дубликатов без учёта регистра; лимит 20 — защитная граница размера состояния, а не фиксированное число режимов.

### 2. Оконный выбор, а не глобальный activeWorkspaceId

Хранить только ID выбранного workspace в `sessionStorage` под отдельным ключом плагина. Согласовать экземпляры полосы, New chat и управления через один оконный store и локальное уведомление, без глобального realtime-события выбора. Использовать существующий React/нативный оконный механизм, без новых библиотек. Проверить, что поверхности SDK действительно разделяют этот оконный контекст.

При отсутствующем/удалённом ID выбирать первый режим; при недоступном sessionStorage сохранять работоспособный выбор в памяти окна и явно не обещать сохранение после reload в таком окружении. Дублированная браузерная вкладка может наследовать исходный выбор, но дальнейшие переключения независимы. `localStorage` и серверный KV не подходят: они делают выбор общим между окнами.

Настройка `enableWorkspaces` включена по умолчанию. Когда выключена, оконный store использует «Работа» (либо первый оставшийся), сохраняет прежний выбранный ID в sessionStorage вместо временного default ID и блокирует выбор другого набора. Включение возвращает действительный прежний выбор. Обе смены повышают поколение и паркуют текущий маршрут без навигации, чтобы поздний ответ или оставленный чат не попал в новый набор. Каталог и содержимое других наборов не удаляются; frontend скрывает переключатель, управление и membership-подменю. При левом положении кнопки список стоит у края перед workspace.

### 3. Явная адресация каждого RPC

Каждое чтение и изменение набора адресуется `workspaceId`: загрузка, sync preview, pin/open, unpin, close, move и favorite. Все пути вызова, включая домашние карточки и восстановление закрытого избранного, должны передавать ID набора, из которого началось действие.

Для существующих форм вызова без ID оставить детерминированный compatibility fallback на мигрированный «Работа», пока он существует. Если такой набор удалён, не направлять legacy-запрос в произвольный первый режим: вернуть ошибку. Явный неизвестный ID всегда отклоняется. Новый frontend всегда передаёт ID.

Глобальная история сохраняет прежний RPC. Создание, переименование и удаление workspace сериализуются той же `mutationTail`. Публичные inputs/outputs проверяются схемами `rpcContract`; неизвестные IDs, неверные имена и лимиты проверяются на сервере, а не только в UI.

### 4. События и ответы нельзя смешивать между режимами

Адресовать изменения содержимого по workspace; отдельное событие изменения списка используется для управления названиями и удаления. Можно использовать namespaced state channels; прежний `tabs-changed` предназначен только для compatibility-набора, не для любого изменяемого workspace.

Уточнение после проверки SDK runtime: `useRealtime` обновляет ссылку на обработчик отдельно от смены подписки. Поэтому само сообщение содержит `workspaceId`, `stateRevision` и state; метаданные коллекции также содержат номер снимка. Номер увеличивается в том же атомарном SQL-write и возвращается RPC. Один оконный store хранит последние принятые номера для отбрасывания старых уведомлений и ответов между поверхностями, не сохраняя выбор на сервере. После восстановления более ранней резервной копии окно перезагружается, чтобы сбросить этот временный watermark.

Ключи очередей, дедупликации и frontend in-flight requests должны включать workspace ID. Ответы принимаются только в поколение выбора, которое начало запрос; после переключения старый результат не заменяет текущие вкладки, workflow activity или ошибку. Нельзя блокировать сохранение уже начатого действия в его исходном наборе. То же касается optimistic UI, pending state, повторной загрузки и reconnect.

Одинаковые наборы между окнами синхронизируются, но глобальное уведомление о создании/переименовании не меняет их выбор. Удаление заставляет сменить выбор только окна, использовавшие удалённый ID.

### 5. Переключатель с восстановлением активной вкладки

Разместить компактный переключатель рядом с существующими контролами полосы, с доступом к управлению из меню. Переиспользовать текущие UI-компоненты. Управление позволяет добавить, переименовать и удалить с подтверждением; отдельный числовой input количества не нужен.

Последний активный ID каждой группы хранить в оконном store и sessionStorage (отдельно от выбора и parked-route marker), с memory fallback и удалением записей исчезнувших workspace. Overlay запоминает маршрут только если чат входит в текущие вкладки и не является оставленным маршрутом прежнего режима. При явном выборе получить свежий адресованный снимок через существующий дедуплицируемый tabs_list, проверить поколение выбора и epoch маршрута, затем открыть сохранённый входящий ID либо первую вкладку. Для пустого набора вызвать openNewThread({ focusPrompt: true }), без tabs_open. Создание нового набора и удаление текущего через диалог используют тот же путь. Поздний ответ после A→B→A или явной смены маршрута не навигирует; устаревшая ревизия получает один повторный запрос. Оконный parked-route marker защищает предыдущий чат, пока восстановление ожидает ответ; смена маршрута снимает marker. Восстановление уже открытого целевого ID снимает marker без добавления preview. После reload первый render также не вставляет оставленный чужой чат в набор; последующая явная навигация использует прежние правила preview.

Посещение New chat относится к конкретному workspace: retained карточки и возможность undo не переносятся между режимами. При уходе из workspace этот visit-local экран заканчивается; возврат показывает сохранённое содержимое. Pending действие относится к исходному workspace. Длинные имена ограничиваются визуально, но полное имя остаётся доступным; desktop/mobile и 44px targets сохраняются.

### 6. Жизненный цикл чата остаётся глобальным

Archive/delete и startup reconciliation обходят вкладки и избранное всех режимов, включая неактивные. Существующие bounded lookup, кэш и чтение parentThreadId переиспользуются для объединённого списка уникальных thread IDs, без дублирования запросов на одинаковые чаты. Ошибки доступа/сети не трактуются как удаление.

Изменённый envelope сохраняется одной операцией; history tombstones обновляются в той же очереди. Разархивирование восстанавливает только прежнюю возможность навигации по истории, не принадлежность к наборам. Удалённые из набора lifecycle-событием ID включаются в его ограниченный список закрытых: startup overlay не восстанавливает прежний preview; явная навигация с `reopen: true` снимает запрет. Закрытие вкладки пользователем остаётся локальным конкретному workspace.

## Risks / Trade-offs

- Задержанный ответ возвращает старый режим → ID в запросе, поколение выбора в frontend, scoped realtime и воспроизводимый тест с отложенным RPC.
- Поверхности показывают разные workspace в одном окне → один оконный store и интеграционный тест полосы/New chat; проверить реальный SDK runtime до закрепления механизма.
- Первый render автоматически создаёт чужой preview → сохранять смысл explicit-navigation guards и отдельно тестировать переключение при открытом чате.
- Удаление workspace совпало с действием другого окна → проверять существование ID внутри серверной очереди и не использовать fallback для явно заданного ID.
- Archive/delete оставляет запись в неактивном режиме → lifecycle-тест на несколько наборов и deduplicated startup reconciliation.
- Повреждение нового storage возвращает старые данные → существующий, но невалидный envelope не заменять автоматически legacy-снимком; вернуть ошибку без записи.
- Старый плагин не видит новые наборы после downgrade → сохранить legacy-ключи как исходный снимок и не обещать полноценный обратный перенос изменений.

## Migration Plan

1. Внутри существующей очереди прочитать новый envelope. Если он есть и валиден, использовать его без повторного создания начальных режимов.
2. При отсутствии нового envelope прочитать старое состояние и закрытые IDs, создать три режима и поместить исходный набор в «Работа». Историю не изменять.
3. Сохранить целый envelope одной атомарной записью SQLite. Старые ключи не удалять и не переписывать; при ошибке сохранения возможность повторить миграцию остаётся.
4. Перевести все frontend-вызовы и события на workspace-aware адресацию, затем добавить UI. Не включать новый UI раньше серверного контракта и защиты от stale responses.
5. Перед завершением выполнить `npm run check`, `npm run build`, live-проверку двух окон, desktop/mobile и миграции. После успешных локальных проверок перезагрузить только `tabs`.
6. При регрессии остановить rollout/вернуться к предыдущему build; сохранить новый envelope для восстановления. Legacy-снимок позволяет читать прежний набор, но не содержит позднейших изменений workspace. Перенос актуальных данных обратно требует отдельного явного решения, без автоматического уничтожения нового storage.
